# Decisions

Short, dated, never re-argued without the user. Newest first.

- **2026-11-20: the terminal's 80 x 24 grid cap holds only up to 720 x 720 px; bigger screens get the full grid.** Owner decision. On screens of at most 720 * 720 px (area 518400, any orientation: 800x480, 720x720 and their portraits) the terminal grid stays capped at 80 columns x 24 rows; on larger screens (1024x600, 1280x720, 1920x1080, ...) it is what the text size gives, up to a 255 x 255 safety bound (minimum 20 x 8). `st_viewport::grid_capped`, `max_cols_for` and `max_rows_for` decide it from the logical (post-rotation) resolution; the terminal and the Settings > Screen > Terminal text size notes share them, so the notes stay truthful. The page buffers grow to 255 x 255; the 80 x 24 view (F6, `BIG_COLS` x `BIG_ROWS`) is unchanged. Unit-tested; not tested on a board (`docs/dev/board-tests-settings-trio.md` step 6).

- **2026-11-18: Settings > Screen gets Idle dim level, Terminal text size and Screen size (three roadmap rows, branch `settings-trio`, for v0.10.5).** Design by the Controller from the owner's roadmap rows (2026-11-14 terminal text size, idle dim level, 2026-11-15 screen size); the choices below marked *provisional* were made while building and are open to the owner. **Storage (all three):** flat keys in `~/.config/cardputerzero/config.json` (`idle_dim_percent`, `terminal_font_px`, `screen_diag` + `screen_mm`), written with one `SetManyAndSave`; `install.sh` and the update helper never touch that file, so the choices survive every update and nothing was added to the helper's backup list (`board.conf` and `install.conf` are in it already and are not where the setting lives). The config store has no remove: "Default" / "Auto" write `0` / `""`, which every reader takes as no override (a value that is already the default is not written). Four keys of the 64 the store holds. **Precedence (all three):** board profile < hand edit of `board.conf` (the same file) < the setting; unit-tested. **Idle dim level:** rows Default (shown as "Default (10 %)", the profile's `APPLAUNCH_DIM_PERCENT`, else 10) and 5, 10, 20, 30, 50 %; applied at once (`launcher_media_controls::set_idle_dim_override`, an atomic read by every dim: the clock screensaver and the request socket's idle dim; `idle_dim_percent()` is no longer cached, `profile_dim_percent()` is); the stored level is also set before the display opens (`main()`). `screen off` / `screen on` requests and the idle dim logic are untouched (only the percent they read changed). The row is listed where the Brightness row is a levels backlight, not on an on/off one. A hand-edited level that is not a step gets its own row so that the list shows what is in force. **Terminal text size:** Auto (the size today's rule gives: board.conf's `APPLAUNCH_TERM_FONT` if set and 10 to 48, else 20 px, 14 px on a portrait screen under 480 wide), Small 14, Medium 17, Large 20, XL 24 px (24 added: trivial); read when the terminal page opens (`ui_app_st.cpp`, so the CLI and SSH pages), stored in `terminal_font_px`; `st_viewport::font_px_resolved` is the one precedence function (setting, then `APPLAUNCH_TERM_FONT`, then the display default). Each row carries its grid as a grey note ("57 x 40" = columns x rows), measured with the terminal's own font (JetBrains Mono Bold) and its own clamps (`st_viewport::grid_cols/grid_rows`, shared with the terminal): the terminal never has more than 80 columns or 24 rows (`BIG_COLS`, `BIG_ROWS`; *changed 2026-11-20: that cap now holds only on screens of at most 720 x 720 px, see the next entry*), so on a tall portrait screen the rows stay 24 whatever the size and the note says so truthfully; the roadmap's "57 columns x 40 rows" example was the unclamped grid. A grey hint line says "Columns x rows. Applies the next time the terminal opens." *Provisional:* the note is "57 x 40" with the meaning in the hint, because "57 columns x 40 rows" does not fit a row at 320 px. **Screen size:** Auto (board profile), 2.8, 3.5, 4.3, 5, 5.5, 7, 8, 10.1 in; sets `APPLAUNCH_PANEL_MM` before the display opens at the next start (`screen_prefs::apply_at_start`, called first in `main()`, before PDA mode, which depends on it), so the apps the launcher starts see it too; the grey hint shows the size in use at this start and its source (installer from `/etc/applaunch/install.conf`, setting, board profile) and says a change applies at next start. The mm come from the same formula and the same measured exceptions as `install.sh --screen-size`: `screen_prefs::panel_mm` is a C++ copy of the installer's `screen_mm()` and `tests/test_screen_prefs_model.cpp` runs the installer's own `screen_mm`, `valid_size` and `valid_mm` against it for 17 diagonals x 12 canvases (204 results) (so the two cannot diverge unnoticed; a change to one fails the test until the other follows). The canvas is the launcher's display, landscape side first (the same as the profile's `APPLAUNCH_LOGICAL`; a portrait or PDA canvas gives the same panel). The row is offered where a board profile exists (`APPLAUNCH_BOARD` set and not `zero2w`), as `install.sh` refuses the options elsewhere. "Auto (board profile)" clears only the setting: a size the installer was given stays in `board.conf`. *Provisional:* **no "Custom diagonal" row.** A numeric field exists (`cp0::ui::TextField` with `TextType::Number`) but not as a Settings page; a custom value needs a form page with its own layout, Save / Cancel and error text, which is a UI decision the brief did not settle. Anyone with an unlisted diagonal still has `install.sh --screen-size`, and a diagonal hand-edited into `screen_diag` (with its `screen_mm`) shows as its own row. *Provisional:* the setting does not touch `APPLAUNCH_DIM_PERCENT` (the installer sets 20 for 5 in on the DSI regulator's backlight; Settings > Idle dim level is the place for that). **Look:** each of the three rows has the grey chevron (row-affordance rule) and its value in the list; the sibling Choice rows (DarkTime, PDA mode) have none, *provisional* (the rule asks for it on every list row; the siblings were left as they are to keep their goldens). Toolkit additions, backward compatible and not used by any app yet: `RowSpec::value` on a Choice row is a grey note left of the check mark (empty: the row as before), `CaptionTone::Hint` is a grey status line, and `SettingsChoiceBinding` has four optional looks (`choice_chevron`, `choice_row_value`, `choice_option_note`, `choice_hint`) with defaults that leave every other page as it was; the native host wraps the hint (`set_caption_wrap`) only while such a list is open. Not done: the rows in the legacy roller Settings (native Settings only, as PDA mode), a restart question (none of the three needs one), anything on the board (not tested on a board; `docs/dev/board-tests-settings-trio.md` is the owner-run list).

- **2026-11-15: the installer takes the screen size (`--screen-size`, `--panel-mm`, a question) and a generic profile for a screen that is not listed.** Owner words: "we have a new board ... the screen is detected as a 4.3 inch whereas it's the same as on pi4b. so board.conf is not good. how can we aleviate that screen is correclty recognized during install?" He chose "Install option + question at install" and also a launcher Settings entry later (roadmap row, not built). Then: "the 4.3, 5, 7 sizes are for 800x480 screens we have to also take into account 640x480 screen from 2.8, 3.5, 4, 5 and I don't have all of them. what can a user do to get a screen we did not test to work?" Both: the option and the question. The DSI panels of 4.3", 5" and 7" give software the same facts (ft5x06 touch at i2c 10-0038, the 10-0045 regulator, the same device-tree nodes, the same 800x480 fbdev), so a profile cannot tell them apart. Decided: (1) `--screen-size INCHES` (the diagonal, 1.5 to 15) and `--panel-mm WxH` (exact, wins) set only `APPLAUNCH_PANEL_MM` of the profile (and `APPLAUNCH_DIM_PERCENT=20` for 5 on the DSI regulator), on every profile that has a screen; the deck (`zero2w`, no profile) refuses them (safest: a minimal `board.conf` would change what the deck's service environment does, and nothing can be tested without the deck); the mm come from the diagonal and the profile's landscape canvas, except the sizes the profiles already know (4.3, 5, 7 inch at 800x480: 94x56, 108x65, 154x86; 3.5 inch at 480x320: 79x49), which keep their values (the formula is within 1 to 2 mm and the 7" panel's pixels are not square); a result equal to the profile's own size leaves the profile byte for byte as it was. (2) Recorded in `install.conf` (`screen_size=`, `panel_mm=`), replayed by Settings > Updates; a hand-edited `board.conf` is still kept unless `--force`. (3) A question ("What is the screen's diagonal in inches? ...") only from a terminal (stdin and stdout), on a first install (no `screen_size=` in `install.conf`), with a profile, no option, not on a PC, never with `--dry-run`, `--plan` or `--board-only`, never from the update helper. (4) `--board generic` (and `--force` on an unknown board with exactly one panel) writes a profile from the detected facts for an untested screen, says so, and asks for the probe report; no deck PWM overlay is added for it. The README says what a user can do ("My screen is not listed"). Built for 0.10.4.

- **2026-11-14: removable drives are mounted through udisks by a polkit rule the installer writes ("Launcher installer first").** Owner answer to how to fix "session not allowed to mount drives". Reason (verified on the HackBerry, Debian 13): the launcher runs as the user service `cyberdeckzero.service` of the lingering user; logind puts it in a background session (Class=background, Active=no, no seat), and polkit's `allow_active` only covers the active session of a seat, so `udisksctl mount -b /dev/sda1` from the launcher or an app (Vinyl: mount on request) is refused. Done: `install.sh` writes `/etc/polkit-1/rules.d/53-cyberdeckzero-udisks.rules` in every variant for the `--user` user only, allowing `org.freedesktop.udisks2.filesystem-mount` and `-mount-other-seat` (removable media); not `filesystem-mount-system`, encryption, loop devices or modify-device. `uninstall.sh` removes it, `--dry-run` lists it, `--plan` has `udisks_rule=`; harmless on desktop boards. App contract: apps may `udisksctl mount -b` and unmount what they mounted.

- **2026-11-13: the Store is forked to carry one patch; Settings > Apps installs no Recommends.** Owner decision. Settings > Apps runs the bundled Store's package helper; when an app's Depends are missing it ran `apt-get -y install <file.deb>`, and boards have apt Recommends on, so an app depending on FFmpeg's libraries pulled about 462 MB on a Lite board instead of about 104 MB (Vinyl P2, report 060). The submodule `projects/AppStore` now points at our fork `OSRdesign/cyberdeck-zero-store` (upstream `CardputerZero/Store` b02db12 plus one commit: `apt-get -y --no-install-recommends ... install`, branch `no-install-recommends`, MIT notice kept). The rule "the Store submodule is not changed by us" stays, except for this patch: any further change needs an owner decision. Apps list every library they need in `depends`; `recommends` are not installed by Settings > Apps (an app whose Depends are already met is installed with `dpkg --install`, which never installed them either). Mesh Hop and mmWave Radar recommend `bluez`: Bluetooth works there only when BlueZ is already on the board. `pizero2w/build.sh --with-store` refuses Store sources without the patch (a WSL tree seeded with the old upstream copy): run `git submodule update --init projects/AppStore` in the checkout. This supersedes "the bundled Store unchanged" in the 2026-10-22 entry and "cannot be changed" in the 2026-10-05 entry.

- **2026-11-12: an app design QA role, `app-design-qa`, blocking at release.** Owner decision, after two header mistakes in the Vinyl screen drafts (app chips, a counter and a volume level with a Bluetooth icon, drawn into the launcher's top band; the app's name written in the band at 320x480, where the launcher shows only the Esc and the status strip): such errors are to be caught by a checklist, not by the owner's eye. (1) **Blocking at release:** advisory while an app is built; at a publish an unresolved FAIL stops it until it is fixed or the owner waives it in writing (the owner's words recorded in the QA report). (2) **Scope:** the app's code and its headless screenshots only (plus a short review of screen drafts, ruling R-6); no board and no `deck-verifier`-style run (token cost). (3) **When:** once as an audit of every existing app (a separate task), then on every app change. Rulings the same day: 7 mm is a recommendation, not a requirement (R-4: WARN; the owner: "if for some reason UI do not allow it, it's down to me to decide usability"); nothing is drag-only (R-1); the README key table is enough (R-2); apps showing outside text use the CJK fallback (R-3); an app's body colours are its own design (R-5). The checklist is `checklists/app-design.md`, its scene set `checklists/app-design-scenes.md`, the agent `agents/app-design-qa.md`; `ROLES.md` (lifecycle step 3, Design QA), `checklists/release.md` (App publishes) and `agents/apps-dev.md` follow.

- **2026-10-18: the native page header's Esc stays 9 mm.** Owner decision, amending the 5/7 mm entry below: the header Esc (`cp0_ui_roller_page`) is excluded from the 7 mm rule and keeps its pre-change size (102 px wide on the deck at 11.3 px/mm), the same in the launcher and every app. It takes the stock-app toolbar keys' constant through `cp0_ui_toolbar_key_px` (`CP0_UI_TOOLBAR_KEY_MM_X10`, at least `CP0_UI_TOOLBAR_KEY_FLOOR_PX`), height still clamped inside the bar's margins; `CP0_TOK_TARGET` stays 7 mm for buttons, action bars and dialog buttons.

- **2026-10-18: the Calculator is exempt from the touch-target token and fills the screen.** Owner decision: the built-in Calculator's keypad is not sized from `CP0_TOK_TARGET` (no 1.3 x TARGET cap, no 75 % floor, no 640 px width cap, no 2.4:1 aspect cap). On every computed canvas (`page_app/calculator_layout.hpp`) the 6x4 keypad spans the full width between the `SPACE_M` margins and runs down to the bottom margin; the display above it takes at most 22 % of the room under the header, with the biggest result font up to 48 px that fits there (the source line 7/12 of it) and no more height than that font needs; the keys get all the rest. Keys may stretch wide; on a very tall screen a key stops at 1.5 x its width and the display takes the extra. Key labels come from the key (55 % of its height, at most 45 % of its width, snapped to the even builtin sizes). Gaps (`SPACE_S`), margins (`SPACE_M`) and radius (`RADIUS_M`) still come from the tokens. The pinned deck 640x480 and Pi 3A+ 480x320 presets already fill the screen and keep their pixels.

- **2026-10-18: two standard touch sizes, 5 mm and 7 mm; the 9 mm target is dropped.** Owner decision: lists already work at 5-7 mm on touch (CompactList 5 mm, rows 7 mm), so a separate 9 mm class for buttons was inconsistent. Standard now: 5 mm for rows where a tap only selects (`CP0_TOK_LIST_ROW_H`), 7 mm for everything that acts (buttons, action bars, dialog buttons, rows that act: `CP0_TOK_ROW_H`; the header Esc was in this list until the same day's amendment above keeps it 9 mm). `CP0_TOK_TARGET` stays as a name for compatibility and equals the row value (7 mm); its pixel floor goes from 48 to 44 px (the usual finger minimum; the floor applies below 6.3 px/mm, e.g. the Pi 3A+ at 6.1 px/mm gets 44 instead of 55). The stock-app toolbar (pinned 140 deck / 100 Pi 3A+, computed sizes 9 mm keys) and the on-screen keyboard (keys and 9 mm Esc/Tab/Ctrl) keep their sizes: they have their own constants (`CP0_UI_TOOLBAR_KEY_MM_X10`, the OSK's) and no longer derive from TARGET. App-facing: `screen.state` `target=` is now 7 mm (79 px deck); the apps repo's APP-GUIDELINES and layout checker change separately.

- **2026-10-05: Settings > Apps decisions (task 006).**
  - The home grid order is stored in the launcher's own config (`app_order` in `~/.config/cardputerzero/config.json`,
    FNV-1a keys of the `.desktop` names), because the Store backend (`projects/AppStore` submodule) cannot be changed.
  - Versions are compared the Debian way (`dpkg --compare-versions` semantics), never as text.
  - Sync failure reasons come from a curl probe of the source, because `--edit-registry` exits 0 for an unreachable
    source (it prints `REGISTRY UPDATED ... cached`). A source counts as synced only on a positive `ok`. The probe
    needed `execvp` in `run_program`: `execv` does not search PATH, so a bare `curl` never started.
  - After a failed install the backend's `pending-package.json` is parked aside
    (`pending-package.parked.<id>.<action>.json`) so other apps install, and it is restored before a retry of the
    same app, which then resumes. Deleting it would break that retry. After a wrong password or Esc the file may stay
    until the next operation; it blocks nothing.
  - Letter shortcuts compare the physical key code, not the ASCII value. W, E, R, T have evdev codes 17 to 20, equal
    to LVGL's up/down/right/left, so a real W/E/R/T press is recorded and the matching native key within 300 ms is
    ignored (same approach as Wi-Fi Survey). Real arrows and F/X/Z/C still work.
