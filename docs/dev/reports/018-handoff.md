## 2. Per-board app data (item 3, the bug)

**Cause.** `Store` kept one set of files in `~/.local/share/mesh-hop` and loaded them before any board had spoken, so whatever board was plugged in next saw (and extended) the same history, read marks, mute flags, groups and ignored nodes. The contact and channel caches were reloaded from the board a second later, which is why "contacts and channels followed the board" but the rest did not.

**Design.**

| What | Where |
| --- | --- |
| Board identity | the 32-byte public key of SELF_INFO (`Model::select_board`, called by `Model::set_self`); the folder is the first 12 hex digits |
| Per-board folder | `~/.local/share/mesh-hop/boards/<12 hex>/`: `messages.jsonl`, `read.txt` (read markers), `contacts.jsonl`, `channels.jsonl`, `prefs.txt` (`mute`, `advert` = scheduled advert, `ignore` = ignored Nearby nodes), `groups.jsonl` + `groups.bak` |
| Global (unchanged place) | `prefs.txt` (now only `retry <attempts> <reset after>`: the message retry rules are about the deck), `presets.jsonl`, `port`, `mesh-hop.log` |
| No board known yet | the model is EMPTY (no history, no cached contacts): Chats shows an empty list and "No board yet. Plug in a MeshCore board: its own conversations appear here." Nothing is written |
| First SELF_INFO, or a SELF_INFO with another key | `Model` drops everything scoped to a board (contacts, channels, "added" names, messages, read marks, mute flags, ignored nodes, groups, advert schedule, Nearby list, statistics), bumps `board_epoch()` and tells the listener; `Store::board_changed` loads that board's folder. The same key again (reconnect, reboot, APP_START refresh): nothing happens |
| UI | `App::tick` sees the epoch change and calls `on_board_changed()`: closes any box / editor / search / statistics / details / Nearby / select mode, forgets the open conversation, the selection, the group filter, the search state and the unsaved radio edits, rebuilds every list (unread totals and the Chats badge follow from the loaded data). Unplugging a board changes nothing on screen until the next SELF_INFO (the footer says "board: not found" / "Board disconnected") |

**Migration (first start of the new layout).** At the first SELF_INFO, if the old flat files are in the data folder (`messages.jsonl`, `read.txt`, `contacts.jsonl`, `channels.jsonl`, `groups.jsonl`, `groups.bak`, and the `mute` / `advert` / `ignore` lines of `prefs.txt`), they are COPIED into that board's folder and the originals are renamed `<name>.pre-boards.bak` (`prefs.txt` keeps only the `retry` line, the original is kept as `prefs.txt.pre-boards.bak`). Nothing is deleted; a file already present in the board folder is kept and the old copy is only renamed; the next start finds nothing to move. The board connected at that moment gets the old history, so **start the first 0.2.2 run with the board whose chats you want to keep** (section 6, step 1). If the wrong board was connected: quit the app, `rm -r boards/<wrong id>`, rename the `*.pre-boards.bak` files back, start again with the right board.

**Disk use.** Each board folder is bounded by the existing limits (200 messages per conversation, 1500 in all, 16 groups, 300 ignored nodes, 350 cached contacts): a few hundred KB per board. The folders of boards that are not connected are KEPT (so that plugging a board back restores it), so the total grows by one folder per distinct board identity (a factory reset creates a new identity, so also by one per reset). **Settings > History** (new rows): **Forget this board's data** (Yes / No box, deletes the saved messages, read marks, groups, mute flags, ignored nodes and advert schedule of the connected board; its contacts and channels, which mirror the board, stay) and **Other boards' data** ("2 boards, 14 KB": Yes / No box, deletes the folders of every board that is not connected; the current board is never touched). The row only appears when there is something to forget.

Files: `core/model.{hpp,cpp}` (board identity, `select_board`, `forget_board_app_data`, `Listener::board_changed / board_data_forgotten`), `core/store.{hpp,cpp}` (per-board paths, migration, `other_boards`, `forget_other_boards`, global retry file), `ui/app.{hpp,cpp}` (`on_board_changed`, no-board state, forget boxes), `ui/ui_logic.{hpp,cpp}` (new rows, prompts, `fmt_bytes`).

## 3. Factory reset (item 4)

**(a) Logging.** `factory reset requested: frame 337265736574 (6 bytes), on the wire 3c0600337265736574, waiting up to 60 s for the answer`; every frame received while it waits is logged with its code, length and first 16 bytes (pushes too); at the end one of: `the board answered with code 0x00, first bytes 00 (OK is 0x00)`, `refused: the board answered with code 0x01, first bytes 0101 (error 1)`, `no answer within 60 s`, `the link went away while waiting for the answer`; and, when the board is back, `the board is back and reports a NEW identity (public key a1b2... instead of c3d4...): the reset happened` or `the SAME identity ... nothing was erased`.

**(b) The frame, settled from the firmware source** (fetched from github.com/meshcore-dev/MeshCore; copies in `C:\CLAUDE\zero7\fw-ref\`):

| Evidence | Fact |
| --- | --- |
| `examples/companion_radio/MyMesh.cpp` on `main` line 1916, tag `companion-v1.15.0` (the user's firmware) line 1873, tag `companion-v1.11.0` line 1600 | `cmd_frame[0] == CMD_FACTORY_RESET && memcmp(&cmd_frame[1], "reset", 5) == 0` (`CMD_FACTORY_RESET` = 51 = 0x33). The same line in all three: the frame is `33 72 65 73 65 74` |
| the last `else` of `handleCmdFrame` (v1.15.0 lines 1949-1950) | an unknown command answers `ERR_CODE_UNSUPPORTED_CMD` (error 1). A bare `0x33` is therefore NOT recognised: it would get "unsupported" |
| `docs/dev/ref/meshcore_py/commands_device.py` `confirm_factory_reset` | sends `b"\x33"` alone and says the firmware "has no token verification": **the reference client is wrong** (it never reaches the reset), its comment is wrong |
| `DataStore.cpp` v1.15.0 `formatFileSystem()` | ESP32: `SPIFFS.format()` then `nvs_flash_erase()`; nRF52 / STM32: `fs->format()`. The identity (`/_main`) is erased with it; the firmware generates a new key at the next start |
| MyMesh.cpp lines 1873-1885 | after the format: `writeOKFrame(); delay(1000); board.reboot();` (and on error `ERR_CODE_FILE_IO_ERROR`). For the USB serial interface `disable()` only clears a flag and `writeFrame` does not look at it, so the OK frame is sent |

So **the frame of 0.2.0 / 0.2.1 (`33 "reset"`) was right**; what I had marked "inferred" is now verified from the source. What most likely went wrong on the Xiao S3: the app waited **10 s** for the OK, the ESP32 SPIFFS format plus NVS erase takes longer (the user saw the link drop about 20 s later), so the app reported "the board did not answer" (a failure) and logged nothing for that timeout, while the board really was erased and restarted. This is an inference (no board here); the new log lines (a) settle it on the next test. If the S3 is now a different board than before the test (new key, no contacts), that confirms it.

**(c) What the app does now** (`core/client.cpp`): the wait is 60 s (`kFactoryResetWaitMs`) with the notice "Erasing the board, this can take a minute..." and the footer "board: reset, restarting" (gold); an OK, a link drop or even silence all keep the state "waiting for the board to come back"; when the board is back the identity it reports decides: another public key = **"Board reset: new keys, no contacts or channels"** (green, held 8 s against the clock notices, footer "board: reset done" for 2 minutes), the same key = "Restarted with the same keys: not reset" (red, "board: NOT reset"). An error answer (refused, unsupported) is the only "failed" case and says so. The board's new identity is simply another board: a new empty folder, the app shows an empty board (no contacts; channel 0 empty, so Settings offers "Add the Public channel"), the old identity's data stays in its own folder (and in "Other boards' data"). The app no longer wipes the cache itself (`clear_board_data` is not called any more; the board swap does the job).
**(d)** nothing else is asked: only the two existing confirmations.

5. **Write on B.** In Chats send a message to the Public channel (and receive one if you can). It appears. ## 7. What I could not verify

* **Nothing ran on the deck and against no real board.** The reset timing (how long the S3 formats), whether its USB link drops before the OK, the new identity it reports (key and name), and that the cause of the failed test was the 10 s timeout, are inferences from the firmware source. The new log lines will show them.
* The first-ever SELF_INFO of a board that has an all-zero or odd key (treated like any key).
* Disk use over many boards on the deck's SD card (bounded per folder, not measured on the Pi). Touch on the real panel for the two new History rows and the forget boxes (same builders as the existing boxes).
* Two boards with the same first 12 hex digits of their key would share a folder (probability about 2^-48; not handled).
* The 8 s hold on the notice "Board reset" against the clock notices was tested in the simulator only.

## 8. Risks and questions for the Controller

1. **The board connected at the first start of 0.2.2 gets the old history.** The protocol says to start with A. Is that the right board (the S3 spare was only used for the reset test)?
2. With no board known yet the app shows nothing at all (as asked), so offline browsing of the last board's history is gone until a board answers. If you want it back later, store the last board id and preload it behind a "last board (not connected)" label.
3. The message retry rules stay global (about the deck); the scheduled advert and the ignored Nearby nodes follow the board (they depend on the board). Say if you want the retry rules per board too.
4. A factory reset makes a new identity, so each reset leaves one old folder (kept, listed in "Other boards' data"). Fine?
5. Every board folder is kept for ever until the user forgets it; there is no automatic expiry. A "forget boards not seen for 90 days" setting is a small addition if wanted.
