# 028 - x86 (amd64) port of the whole stack: launcher, Settings, Store backend, apps

Status: evaluation written 2026-10-21 on branch `x86-port-evaluation` (= launcher main f40705d, v0.8.0). Apps repo read
at origin/main 3dde2c4. Research, a WSL spike and this document only: no product code changed, no board or tablet
touched, nothing merged. It replaces the parked report of 2026-10-07 (branch `docs-later-x86`,
`docs/dev/later/x86-fz-m1/x86-port-options.md`), whose tablet facts it reuses and whose nine decisions it merges
(section 8).

Markers: **M** = measured today (WSL spike, section 2.4) or measured on the tablet on 2026-10-07 over ssh (probe
output on `docs-later-x86`), **V** = verified in the code (file:line), **I** = inferred / documentation / web, needs
the tablet. Owner decisions are **X1-X15** (section 8). Platform assumption (owner): a Debian/Ubuntu-like distribution
with systemd, NetworkManager, BlueZ, and a kernel with DRM/KMS, evdev and libinput.

## 1. Summary and recommendation

**The stack is already almost arch-neutral.** Built natively for x86_64 in WSL with no source change (M): the launcher
(40 s), the Store backend, the vfb shim and five apps (Serial Console, Mesh Hop, System Monitor, Net Toolbox, RSS
Reader). The only build edits were configuration: the two NEON lines out of the LVGL config and a toolchain wrapper.
The real x86 binary ran in WSL on a virtual 1280x800 framebuffer (the launcher's own VFB2 shim). It drew the home grid
at **23 MB peak RSS**. The host render harness drew Settings, the on-screen keyboard (OSK), the terminal OSK, Settings
> Apps, the switcher and the Calculator at the tablet's 1280x800 / 8.42 px/mm with no change. The responsive shell, the
app contract, multitasking and the OSK need nothing new for x86.

**What is Pi-specific is thin and known:**
- **Packaging and install:** `build.sh` and `install.sh` assume aarch64, a device-tree model and `config.txt`. Apps
  ship one aarch64 binary in `root/`, and the registry has no architecture.
- **Three small launcher gaps:**
  - the backlight `sysfs:` kind is not implemented;
  - the always-present i8042 keyboard of a tablet counts as a physical keyboard, so the OSK never opens;
  - battery is bq27-only.
- **Two app gaps:** System Monitor's Pi rows, and viz1090's native binaries and `librtlsdr` soname.

**Recommendation: port the current stack as it is (fbdev + LVGL, no display server), one source tree, per-arch
bundles and per-arch registries.**
1. Keep fbdev: i915 provides `/dev/fb0` (M), and the whole stack shares it (fullscreen apps, the VFB2 handoff, the
   multitasking snapshots).
2. Add an amd64 bundle and an install.sh "pc" profile detected from DMI and EDID.
3. Close the three launcher gaps (about 150 lines).
4. Add `registry-amd64.json` next to the untouched `registry.json`. Settings > Apps picks the registry by
   `dpkg --print-architecture`, and the upstream Store backend needs no change.
5. Rebuild the five LVGL apps for amd64 with a `--arch amd64` mode in `build_app.sh`.

Defer DRM/KMS, Wayland sessions, auto-rotate and viz1090. Cost: phases x-a to x-c (usable tablet with apps) are about
**4-6 worker sessions** plus one 30-minute tablet session per phase. x-d (battery, System Monitor, release) adds 2-3
sessions (section 9).

### 2.3 Where the apps' binaries come from today

Every published app commits its stripped aarch64 binary under `apps/<id>/root/` (V). `tools/make_registry.py` packs
`root/` into `packages/<pkg>_<ver>_arm64.deb` and writes `registry.json`. The download URLs are
`raw.githubusercontent.com/.../packages/..._arm64.deb`. The Store backend only reads `download.url` / `.package`
(`projects/AppStore/main/backend/appstore_native.cpp:965-970`). `curl -fL` follows redirects (`:470-475`), so release
assets would also work. Settings > Apps turns `owner/repo` into `.../<branch>/registry.json`
(`ui/settings/apps_backend.cpp:332`). Nothing in the chain knows an architecture: an arm64 entry would install on
amd64 only to fail with dpkg's "package architecture (arm64) does not match system (amd64)" (I, standard dpkg).

## 3. Display and input stack on x86

| Option | What it means | Fit for this stack | Cost | Verdict |
| --- | --- | --- | --- | --- |
| **fbdev** (today) | launcher and fullscreen apps mmap `/dev/fb0`. On x86 it is the DRM driver's fbdev emulation (`i915drmfb`, 1280x800 32 bpp on the tablet, `DRM_FBDEV_EMULATION=y`, `FB_DEVICE=y`, M) | everything works as designed: one shared surface for the launcher, fullscreen apps (they open fb0 themselves), the VFB2 compat handoff and the multitasking snapshots (`cp0_display_fb_snapshot/restore`, page = stride x height = **4.0 MB** at 1280x800 vs 1.2 MB on the deck). It also works in a VM (virtio-gpu / bochs give a DRM fbdev) | 0 | **use it** |
| DRM/KMS dumb buffer | the launcher becomes DRM master, makes a dumb buffer and sets the CRTC | breaks the shared-surface model: fbdev writes of apps do not show while another master owns the CRTC. Every app, the handoff and multitasking would need master hand-over (drop master, the kernel restores fbdev only on last close). LVGL's own DRM driver does not replace our output stage (rotation, compat window, overlays) | 300-500 lines + all apps' backend + board tests | later, only if a target distro drops `/dev/fb0` |
| SDL2 (`linux_x86_sdl2_config_defaults.mk`) | LVGL simulator backend | SDL builds swap the services for simulator stubs (`ext_components/cp0_lvgl/SConstruct:75-86`, `src/sdl/`), so there is no real Wi-Fi/BT/process control. Usable inside a desktop session only | build split + services rework | no (dev tool only) |
| Wayland/X kiosk (cage, labwc, sway) | launcher as a client; apps as windows | the VFB2 compat model, fb handoff, snapshot/restore, hold-Esc watchdog and the shared top bar all assume one framebuffer. Every native app would become a Wayland client. More RAM (I: compositor 30-80 MB). labwc GPL-2, wvkbd GPL-3 as separate processes (repo stays MIT) | large (the old report's option B: 1,500-2,500 lines, 8+ sessions) | no. An on-demand "desktop program" session (old option D, `X-Session=wayland`) stays an optional idea |

**Input.** evdev and libinput as today. The tablet's touch is I2C-HID `hid-multitouch` (M), found by capability,
with buffer orientation and ABS-range normalisation (no calibration file). The panel is natively landscape, so
`APPLAUNCH_ROTATE=0` (M). Portrait and auto-rotate (the ISH `dev_rotation`/accel sensors are present, M) stay out, as
decided for all boards in 014.

**Hi-DPI.** The layout service sizes everything by px/mm (8.42 on the tablet, 11.3 on the deck). The tablet's
fbdev reports no mm (I, as on the other KMS boards), so the profile must set `APPLAUNCH_PANEL_MM=152x94`. install.sh
can read it from the connector's EDID (bytes 21-22 cm, or the detailed timing mm: 152x94 measured).

**Risks to check in x-a.**
1. **i915 fbdev CPU writes reach the panel.** Expected (I): VLV/CHV have no FBC, and PSR support for them was removed
   from i915.
2. **Readback cost.** The snapshot reads the uncached mapping: about 10 ms per 1.2 MB on the deck (comment at
   `cp0_lvgl_dpi_scaled.c:973-974`). 4 MB on an Atom: I estimate 30-80 ms per switch, which is acceptable.
3. **Full-frame redraw.** Software LVGL at 1280x800 on Atom x5. I estimate 15-40 ms; the first measurement is in
   x-a.
4. **Touch contacts.** An Ubuntu bug report says the FZ-M1 mk2 touch reports only **2 contacts** (I,
   [LP 1739792](https://ubuntu-bugs.narkive.com/D9t3LC2Z/bug-1739792-new-touchscreen-input-on-panasonic-fz-m1-only-detects-two-fingers)).
   If `ABS_MT_SLOT` max is 1, the 3-finger switcher gesture cannot fire. The HackBerry has the same limit and uses the
   clock long-press (G2) and Alt+Tab instead (multitasking notes). Measure with `evtest` in x-a.

## 5. Packaging and distribution

**Launcher bundle per arch.** `build.sh --arch arm64|amd64` writes `cyberdeckzero-launcher-<ver>-<arch>.tar.gz`. A
GitHub release carries both assets. install.sh checks that the bundle's arch matches `dpkg --print-architecture` (a
one-word `payload/ARCH` file) instead of `uname -m = aarch64` (`install.sh:693`). The legacy `pizero2w-bundle.tar.gz`
copy stays arm64-only.

**Apps: one repo, two registries** (recommended, X8).
- **Overlay.** `app.json` gains `"arch": ["arm64", "amd64"]` (default `["arm64"]`, so nothing changes for existing
  apps). Arch-specific files sit in an overlay `apps/<id>/root.amd64/` with the same paths as `root/`; `root/` keeps
  the arm64 binary, so existing tooling and history stay. `build_app.sh --arch amd64` writes the stripped binary into
  that overlay.
- **Packages.** `make_registry.py` builds `packages/<pkg>_<ver>_<arch>.deb` from `root/` + `root.<arch>/` (the
  `build_deb.py --arch` it already has). It writes `registry.json` (arm64, unchanged) and `registry-amd64.json` (only
  apps listing amd64).
- **Settings > Apps.** `apps_backend.cpp:332` builds `.../registry-<arch>.json` when the system arch is not arm64
  (about 10 lines). `default-sources.sh` seeds the same name. The upstream Store backend (submodule, unchanged per the
  rebrand constraints) just sees a registry whose URLs are amd64 packages. Decks keep reading `registry.json`.
- **Rejected.** A per-app `downloads.{arch}` map in one registry would need a Store backend change. Filtering in the
  launcher alone cannot stop the backend from offering arm64 entries.
- **Size.** `packages/` is 76 MB of debs today (V); one amd64 set adds about 35 MB (I). Release assets (curl `-fL`
  follows) are the alternative if the repo grows too much.

**LAUNCHER_REF.** One pin for both arches: `cp0_lvgl` is arch-neutral, and both builds use the same commit
(`apps/_common/LAUNCHER_REF`, today 45d99a9). `build-info` records the arch (`stamp`, `build_app.sh:129`).

**Build hosts.** amd64 builds natively in WSL (M: 30-45 s per app, 40 s launcher). WSL Ubuntu 24.04 output needs
GLIBC_2.38, the same floor as the arm64 builds. Needed once on the build box: the -dev packages (X9). arm64 stays
cross-built with the SDK sysroot. No CI now (X15). GitHub has x86_64 and arm64 Ubuntu runners if wanted later.

## 6. Test strategy without hardware, then short physical tests

**On the PC (no tablet).**
1. **Render harness.** Add 1280x800 at 842 px/mm as a review size (no golden) to the scenes touched by the port
   (home, Settings, Apps, OSK, switcher). M: they render today with a scene override.
2. **Unit tests.** `cp0-unit` / `app-unit` already run on x86_64. Add tests for the keyboard ignore list, the
   `sysfs:` backlight and the arch-aware source URL.
3. **install.sh in SYSROOT mode** (`pizero2w/tests/test-install-board.sh`). Add a fake `/sys/class/dmi/id`, a DRM
   connector with an EDID blob, `intel_backlight`, `x86_64`. This checks the pc profile and that no boot file is
   touched.
4. **x86 smoke run.** The spike's trick: the real amd64 binary with the native vfb shim `LD_PRELOAD`ed on a
   1280x800 shm framebuffer, then PNG and RSS. It could become `tools/dev/x86-smoke.sh` (about 60 lines). It catches
   link and start-up failures and the profile's geometry.
5. **Optional VM.** QEMU with virtio-gpu (gives a DRM fbdev) and `virtio-multitouch` (a DIRECT touchscreen; QEMU 8+,
   I). It is not worth setting up before x-a unless KVM works in WSL (unverified).

**On the FZ-M1 (owner, about 20 minutes per phase, main path only):**
1. Boot: the grid comes up by itself, the boot lines do not draw over it. Tap a tile, drag a list.
2. USB keyboard: arrows, Enter, short Esc back, Esc hold 3 s quits an app.
3. Unplug the keyboard: tap a text field (SSH form) and the CLI, and the OSK opens. Plug it back: the OSK goes.
4. Settings: Wi-Fi connect, Bluetooth pair the keyboard, brightness, shutdown.
5. Settings > Apps: add the source, install Serial Console or System Monitor, open it, switch apps (3 fingers, or
   clock long-press / Alt+Tab).

## 8. Risks and owner decisions

**Risks.**
- **i915 fbdev writes.** Expected fine (section 3), checked first in x-a.
- **2-contact touch.** The switcher gesture may be unavailable; fallbacks exist.
- **Software rendering speed** at 1280x800 on Atom is unmeasured.
- **Distro package names differ** (librtlsdr0/2, t64 renames). The launcher's own Depends (`libinput10 libxkbcommon0
  libfreetype6 curl`) exist on both (M for Ubuntu 24.04 candidates).
- **Networking hand-over.** Moving the tablet from netplan/networkd to NetworkManager can cut ssh: do it on the
  console.
- **fbdev removal by future distros** would force the DRM work of section 3.
- **Licence.** The launcher binary is already GPL-3 as a whole because of `tree.hh` (decision 2026-10-13); x86 adds
  no GPL code. viz1090 already ships GPL-3 readsb, and a bundled librtlsdr (GPL-2) would sit beside it as a separate
  library with its notice.

**Decisions** (the 2026-10-07 numbers in brackets):
1. **X1 Approach [1].** fbdev + LVGL as today, no display server, DRM and Wayland deferred. *Rec: yes.*
2. **X2 Supported amd64 systems.** glibc >= 2.38 systems (Debian 13, Ubuntu 24.04 / 26.04, Armbian on them). The
   owner's FZ-M1 on Armbian Ubuntu 26.04 is the reference. *Rec: yes; stay on Armbian 26.04 [8b].*
3. **X3 Tablet system changes [2].** Install `network-manager` and `bluez`, and hand Wi-Fi from netplan/networkd to
   NetworkManager on the console. *Rec: yes, install.sh offers the packages, the owner does the switch once.*
4. **X4 OSK on the tablet [3].** Same rule as every board: automatic only when no physical keyboard is present,
   never summoned. The 2026-10-07 idea of a manual toolbar toggle contradicts the 2026-10-10 policy. Add an Alt key
   to the terminal layout? *Rec: same rule, no toggle; Alt key yes (small, all boards).*
5. **X5 What counts as a keyboard [5].** Ignore the i8042 `AT Translated Set 2 keyboard` on the tablet and any named
   device (the barcode scanner) through `APPLAUNCH_KBD_IGNORE` in `board.conf`. *Rec: yes, pc profile default
   `bus:0011` when the DMI chassis is a tablet (type 30/32).*
6. **X6 Device profile [4].** Keep the one compile-time profile (`APPLAUNCH_HW=pizero2w`) for amd64; everything
   hardware-dependent is runtime (`board.conf`). *Rec: yes (renaming the token is optional cosmetics).*
7. **X7 Orientation and density [6].** Landscape only. Density from EDID mm, written by install.sh. *Rec: yes.*
8. **X8 Apps packaging [7].** One apps repo, `root.amd64/` overlays, `registry-amd64.json` beside the untouched
   `registry.json`, amd64 debs in `packages/`. *Rec: yes; release assets only if the repo gets heavy.*
9. **X9 Build box [8a].** One-time `sudo apt install libinput-dev libxkbcommon-dev libudev-dev libdbus-1-dev
   libglib2.0-dev libsdl2-dev` in WSL (owner runs it), instead of the spike's private sysroot or a Debian container.
   *Rec: apt install (simplest; libsdl2-dev only for viz1090).*
10. **X10 Boot look [9].** install.sh leaves GRUB and the kernel command line alone (boot lines visible, as on the
    deck). *Rec: yes.*
11. **X11 Releases.** One GitHub release with `-arm64` and `-amd64` bundles; README "Install" gets an x86 line.
    *Rec: from the first release after x-b.*
12. **X12 Battery.** Battery icon in the status strip and Settings > Battery when a `power_supply` battery exists
    (helps every battery board). *Rec: yes, phase x-d.*
13. **X13 Store tile and M5 hub on amd64.** Hide the tile and do not seed hub sources (their packages are arm64).
    *Rec: yes.*
14. **X14 viz1090 on amd64.** Defer to x-d. Then build for Ubuntu only (librtlsdr2), or bundle librtlsdr in
    `/opt/viz1090`. *Rec: defer, then bundle.*
15. **X15 CI.** None; WSL builds as today. *Rec: no CI now.*
