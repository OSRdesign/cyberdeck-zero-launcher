# 040 - PDA profile, phase S2: a portrait launcher, no writing zone

Status: built 2026-10-25 from report 038 (sections 2-4, 7-12; owner defaults of section 12 accepted: profile "PDA",
the 480x800 4.3" DSI the reference, 480x640 for 3.5-4" panels, landscape apps shown and run turned (option b),
"letterbox" dropped, `X-Portrait=WxH`, multitasking on when the short side is at least 480). Worktree
`launcher-pda-s2`, branch `pda-s2-portrait` from `github/main` 7bfb4b3 (v0.8.7). Nothing committed or pushed, no board
touched. The writing zone (S1, S3) is not part of this phase: text is typed (a keyboard, else the fallback on-screen
keyboard).

## 1. Summary

- **Profile:** `install.sh --board pi3a-wsdsi43-portrait` writes the DSI panel's profile turned to portrait
  (`APPLAUNCH_LOGICAL=480x800`, `APPLAUNCH_ROTATE=90`, no `APPLAUNCH_COMPAT_SCALE`). Never detected. The landscape
  `pi3a-wsdsi43` profile text is byte-identical (same checksum line as v0.8.7: installed boards are not rewritten).
- **Status strip:** on a computed canvas under 600 px wide the strip is drawn at the Compact scale (72 %, 230 px), as
  report 038 section 4 proposes. The page title budget at 480 wide goes from 131-135 px to 192-196 px: "Settings",
  "Open apps", the section titles fit. The pinned 640x480 and 480x320 are untouched.
- **Narrow page header (owner decision, after the first build):** on the portrait panels the shared page header draws its
  title at 18 px (32 elsewhere), so every launcher page title fits, the longest "On-screen keyboard" included, and a
  breadcrumb title ("Settings > Screen", an app's "Net Toolbox > Diagnosis") shows its last part only (section 4).
- **Multitasking:** on where the short side is at least 480 (`switcher_fits`), so 480x640 and 480x800 have the switcher.
  A switcher card whose first word does not fit beside its X now starts the name under the X (no "Ser" / "ial Con...").
- **Landscape apps turned:** a fullscreen app without `X-Portrait` on a portrait launcher is shown and started with the
  panel's landscape canvas: the report's mechanism (per-launch `APPLAUNCH_ROTATE` / `APPLAUNCH_LOGICAL` /
  `APPLAUNCH_SCREEN_*` overrides) verified against the code and kept, with one detail settled (section 3.4: the
  rotation is a quarter turn back from the launcher's, 90 -> 0). `X-MinSize` is checked against that landscape canvas,
  `X-Portrait` against the portrait one.
- **Tests:** unit tests for every pure piece, the install tests, PDA harness scenes with goldens at 480x640 and 480x800,
  the contract probe on the turned environment. The 77 goldens at 640x480 and 480x320 are byte-identical (section 6).
- **Open:** `screen.state` still describes the portrait panel for a turned app (S4). The cut titles of the first build
  are resolved (section 7, item 1).

## 3. Landscape apps turned (report 038 section 3.2, option b)

### 3.1 The rule (`desktop_entry.cpp`, `desktop_fit()`)

| Launcher canvas | App | Result |
| --- | --- | --- |
| landscape or square (every board but the PDA) | any | as before: `X-MinSize` against the canvas (`Native` or `Hidden`) |
| portrait (`h > w`) | compat (320x170) or terminal | as before: `X-MinSize` against the canvas; never turned (it runs in the launcher's 1x window) |
| portrait | fullscreen with `X-Portrait=WxH` that fits the portrait canvas | `Native`: the portrait canvas |
| portrait | fullscreen without `X-Portrait`, or one that does not fit | `Turned` when `X-MinSize` fits the landscape canvas `h x w`, else `Hidden` |

The brief's "X-MinSize against the portrait canvas for portrait-declared apps" is implemented as "`X-Portrait` against
the portrait canvas": `X-MinSize` keeps its landscape meaning (038 sections 3.3 and 7), so checking a portrait-declared
app's `X-MinSize=640x480` against 480x800 would hide every such app.

### 3.2 The mechanism, checked against the code

| Report 038 claim | Checked |
| --- | --- |
| a fullscreen app inherits the board geometry and runs its own `cp0_lvgl` backend | yes: the apps' `_common/platform.cpp` only adds `APPLAUNCH_DISPLAY` / `APPLAUNCH_APP_MODE` when missing, no geometry; the backend reads `APPLAUNCH_ROTATE` (`cp0_lvgl_dpi_scaled.c:1091`) and `APPLAUNCH_LOGICAL` (`:1103`) |
| overriding them per launch makes it a landscape app on the same panel | yes: the exports are put in front of the app's `sh -c` line (`launch.cpp`, both the blocking and the supervised path); the backend then sets up 800x480 at rotate 0 on the 800x480 buffer |
| touch follows | yes: `APPLAUNCH_TOUCH_ORIENT=buffer` maps through the app's own rotation (`cp0_lvgl_dpi_scaled.c:368-369`) |
| `APPLAUNCH_SCREEN_*` must follow too | yes, and it matters: viz1090's glue takes `APPLAUNCH_SCREEN_ROTATE` before `APPLAUNCH_ROTATE` and `APPLAUNCH_CANVAS` / `APPLAUNCH_SCREEN_W/H` for its size (apps `viz1090/src/core/viz_screen.h:8-14`) |
| the app does not rewrite `screen.state` | yes: `cp0_ui_state.c:130` skips the publication when `APPLAUNCH_APP_MODE` is set |
| snapshot / restore of multitasking copy raw pages | yes (`display_handoff`, supervisor): rotation does not matter; the hidden app's dimmed frame shows sideways behind the portrait switcher (accepted in 038) |

### 3.3 What a turned app gets (`app_launch_env.cpp`, `turned_from_metrics()`)

On the Pi 3A+ DSI portrait (480x800, rotate 90), after the contract's own variables:

```
APPLAUNCH_CONTRACT=1 APPLAUNCH_APP_MODE=fullscreen APPLAUNCH_WINDOW=0,0,800,480 APPLAUNCH_CANVAS=800x480
APPLAUNCH_CANVAS_SCALE=1 APPLAUNCH_STATE_DIR=... APPLAUNCH_ROTATE=0 APPLAUNCH_LOGICAL=800x480 APPLAUNCH_SCREEN_W=800
APPLAUNCH_SCREEN_H=480 APPLAUNCH_SCREEN_ROTATE=0 APPLAUNCH_SCREEN_CLASS=wide
```

`APPLAUNCH_SCREEN_PPMM` is inherited: the density is the mean of both axes, the same either way (unit-tested).

### 3.4 Deviation: the rotation of a turned app

Report 038 writes "`APPLAUNCH_ROTATE=0`, the panel's native rotation". That holds for `ROTATE=90`. With the owner's
other choice, `ROTATE=270`, rotate 0 would make the user turn the device the other way for every app. The rule built is
`turned_rotation()` = a quarter turn back from the launcher's (90 -> 0, 270 -> 180, 0 -> 270, 180 -> 90): the same turn
of the device whatever side is up, and exactly 038's value on the reference set-up. Rotate 180 is a supported output
rotation (`cp0_fb_output.h:13`) but no turned app has run at 180 on a board yet (I).

- **Strip (`cp0_ui_metrics.c`):** `NARROW_STRIP_BELOW_W 600`, `NARROW_STRIP_PCT 72`: on a computed canvas under 600 px
  wide, `shell.status_pct` = 72, `shell.status_w` = 230 and `tok[STATUS_PCT]` = 72. The bar height, its top margin
  (so the header's 40 px Esc), the title size and every other number are unchanged. It also applies to 320x480 and
  480x480 (no board) and reaches apps with their next pin of `cp0_ui_metrics.c`; apps run turned today, so nothing
  changes for them now.
- **Switcher rule (`switcher_model`):** `kSwitcherMinSide = 480`, both sides. New in: 480x640, 480x800 and 480x480
  (the earlier test expected 480x480 off: changed deliberately). Still off: 480x320, 320x480, 320x170. The log line
  says "short side under 480". With S3 the rule must stay on the panel's size, not the app area (480x434 would be off).
- **Name wrap (`switcher_view.cpp`):** when the name's first word is wider than the line beside the X but fits the
  card's width, the name starts under the X. It only triggers on narrow cards (480x640 at 11.3 px/mm); at the
  reference densities (8.5 and 9.0 px/mm) "Serial" fits beside the X and nothing moves.
- **Narrow page header (`cp0_ui_metrics.c`, `cp0_ui_roller.c`, `cp0_ui_page.cpp`):** `cp0_ui_narrow_header(m)` is true
  on a computed canvas under 600 px wide drawn with the deck's shell (400 px high or more): 480x640, 480x800 (also
  480x480, 320x480, 599x800; no board). There:
  - `shell.title_px` = 18 (`NARROW_TITLE_PX`) and `shell.title_y` + 7 (half the 14 px it lost: the title stays centred
    on the 32 px title's line, 17 instead of 10). The home grid has no title, so only the page headers change; the
    header check (title origin against the home grid's) still holds.
  - `cp0_ui_roller_page_t.title_last_only` = 1: `Page::apply_title()` keeps only the last part of the path, and of that
    part the text after its last `" > "` (an app passing its breadcrumb as one string). Every launcher and app page
    title goes through `Page::set_title()` (apps pass paths such as `{kAppTitle, port_.tty, "Ask"}`), so the rule
    lives there once. The dots of a title still too long stay as the last resort (a long Wi-Fi name, the deck's
    11.3 px/mm on a 480 wide panel: 171 px).
  - The size: the largest Montserrat size whose longest launcher page title fits the 192-196 px left of the Esc.
    Widths from the font's advances (no kerning): "On-screen keyboard" 249 px at 24, 228 at 22, 207 at 20, **186 at 18**;
    "Pointer navigation" 170, "Saved networks" 146, "Keyboard test" 128, "Network Time" 130, "Set Manually" 118,
    "Date & Time" 112 at 18. 24 px (the Compact title) would still cut "Pointer navigation" (227) and "On-screen
    keyboard" and leave "Saved networks" (195) borderline at 480x640; 26 px is the largest that fits the three titles
    seen cut ("Date & Time" 162, "Keyboard test" 185, "Network Time" 187). "Join Hidden Network" (194 at 18) is a dialog,
    "Quit to desktop" a desktop-board page, "Network Time" a toggle row: not PDA page titles.
  - Not changed: 320x170 (narrow, but the Compact shell: its 24 px title and full breadcrumbs stay; the first build of
    this rule keyed on the width alone changed 16 of its review shots, so it is keyed on the shell too), every canvas
    600 px wide or more, the pinned 640x480 and 480x320 (presets, never computed: width alone would have been safe for
    them).
  - Apps get it with their next pin of the cp0_lvgl files (Page and metrics are SDK files they copy).

## 7. Open questions and risks

1. **Resolved: long page titles at 480 px wide.** At 32 px the 192-196 px budget cut Date & Time (199), Set Manually
   (209), Keyboard test (227), Saved networks (259), Pointer navigation, On-screen keyboard. Owner decision: a smaller
   title on narrow screens and breadcrumbs reduced to their last part; built as an 18 px title (section 4), the largest
   size at which the longest title, "On-screen keyboard" (186 px), fits. 18 px is well under the roller's 24-26 px row
   text; if it reads too small on the board, 24 px is the next step (one constant, `NARROW_TITLE_PX`; it cuts Pointer
   navigation and On-screen keyboard with dots) — check in the board test.
2. **`screen.state` for a turned app** keeps the launcher's portrait panel (`w=480 h=800 rot=90`, portrait tokens); the
   app's environment has the landscape canvas. Our apps compute their tokens from their own backend and read only
   `input.state`, so nothing shows; a third-party app taking `screen.state`'s `w`/`h` for its canvas would be wrong.
   038 S4 adds `orient=`; until then section 3 of APP-CONTRACT.md says to take the environment first.
3. **A plain `install.sh` reverts to landscape** (a generated portrait profile is replaced, kept as `.bak`). Documented
   ("pass `--board pi3a-wsdsi43-portrait` every time"). Keeping a generated portrait profile on a plain install would be
   a small rule in `plan_profile()`; not done (a behaviour decision).
4. **Rotation 180 for turned apps** (with `APPLAUNCH_ROTATE=270`) is untested on a board (I). Report 038 had 0 only.
5. **Turned apps behind the switcher** show their dimmed frame sideways (accepted in 038); the legacy sheet's box is drawn
   portrait over it.
6. **Multitasking on 480x480** is new (no board has that canvas). In S3 the switcher rule must keep using the panel, not
   the 480x434 app area.
7. **Repaint speed** of 480x800 RGB565 turned by the CPU on the Pi 3A+: measure in the board test (038 risk).

Board test on the Pi 3A+ with the 4.3" DSI panel (about 30 min):

1. **Keep the landscape profile:** `cp /etc/applaunch/board.conf ~/board.conf.landscape`. The board's profile was
   written by hand (2026-10-13), so install.sh keeps it unless `--force` is given.
2. **Install:** copy the bundle, check `sha256sum -c`, unpack, `cd bundle`, then
   `sudo ./install.sh --board pi3a-wsdsi43-portrait --dry-run`: the profile line must say `write`, `update` or
   `replace`; if it says "edited by hand: kept", run it with `--force` (the old file goes to `board.conf.bak`). Then the
   same command without `--dry-run`, and `systemctl --user restart cyberdeckzero.service` (or reboot).

### 11.3 Home grid speed: image cache on

`CONFIG_V9_5_LV_CACHE_DEF_SIZE=1048576` and `CONFIG_V9_5_LV_IMAGE_HEADER_CACHE_DEF_CNT=32` in the four
`projects/APPLaunch/*config_defaults.mk` (`config_defaults.mk`, `linux_x86_64_native_`, `linux_x86_cross_`,
`linux_x86_sdl2_`; the keys were absent, so LVGL's default 0 applied) and, as `CONFIG_LV_CACHE_DEF_SIZE` /
`CONFIG_LV_IMAGE_HEADER_CACHE_DEF_CNT`, in the harness's `tests/render/config/lvgl_config.h`. The arm64 build's generated
`lvgl_config.h` shows both values.
- All rendered PNGs byte-identical from this item (11.5).
- RAM: at most 1 MB of decoded images (a size-bounded LRU: it evicts the least recently used entries when an insert would
  pass 1 MB), plus 32 small header entries. The Pi Zero 2 W deck has about 414 MB: fine. The cache is not freed under
  system memory pressure (it is LVGL's own bound inside the process's heap, not tied to the kernel's reclaim); it only
  shrinks by its own LRU. It applies to every board built from these files, the deck included (same 1 MB).
- Study numbers (PC, ms per frame): home 5.4-6.2 -> 3.8-4.2 with the cache; Settings 1.2-1.4. Not measured on a board.

### 11.4 Full-height native draw buffer, portrait only

`cp0_lvgl_dpi_scaled.c` (native display): `lines = g.lh > g.lw ? g.lh : 96`. A portrait canvas draws a frame in one
chunk (480x800 RGB565 = 768,000 bytes instead of 92,160 for 96 lines: about 660 KB more RAM). Landscape and square keep 96
lines, so no landscape output changes. Study: PC 3.8-4.2 -> 3.7 ms with the full buffer, 2.5 with both.
Goldens changed by it (regenerated, nothing else): `480x640/pda_home` (19 px differ), `480x640/pda_switcher_three` (5 px),
`480x800/pda_home` (45 px), `480x800/pda_switcher_three` (10 px). The study said 1 LSB: the largest channel delta is 8-9 on
the first three and **57 on 10 pixels of `480x800/pda_switcher_three`** (box x 35..469, y 571..672, the card edges;
anti-aliasing computed over the whole frame instead of per strip). Review-only `480x640/pda_dense_switcher_three` (8 px,
delta 4) and 4 contact sheets also change.
