## 1. The 0.1.2 questions (decided by the user)

* `curl` is in `Depends` (`app.json`: `libfreetype6, curl`; `dpkg-deb -I` shows it).
* One retry of the silent preset download about 60 s after a failed first attempt, while the deck is online. The policy is a small pure class (`PresetSchedule` in
  `core/preset_feed.hpp`, unit tested): first try 4 s after the start once online (offline: looked at again every 30 s), then, only if the first try really ran and failed,
  one more try 60 s later (again only online, again checked every 30 s while offline). At most two tries per launch; none after a success; none when curl is missing or cannot
  start. Still silent (a line in `mesh-hop.log`, nothing on screen), still no "Refresh now". Headless proof (`presets_run.sh` case 9, flaky curl): `19:40:30 refresh failed
  (curl failed, exit code 22) ... one more try in 60 s`, `19:41:30 online, downloading ... (second try)`, `fetched 27 entries`, 2 curl calls.

## 2. The path hash size (new request): how the board reads and sets it

Evidence in the references (all under `docs/dev/ref/`):

| What | Where | Fact |
| --- | --- | --- |
| Read | `companion_protocol.md` lines 684-685; `meshcore_py/reader.py` 437-439 | DEVICE_INFO byte 80 = client repeat (firmware level 9+), **byte 81 = path hash mode (firmware level 10+)**; the reader only reads it when `fw_ver >= 10` |
| Read (CLI) | `meshcore_cli.py` 2928-2939 | `get path_hash_mode` is a DEVICE_QUERY; "Not available" when the field is missing; `commands_device.get_path_hash_mode` returns 0 when absent |
| Set | `meshcore_py/commands_device.py` 403-406 | `set_path_hash_mode(mode)` sends **`3D 00 mode`** (command 61 `SET_PATH_HASH_MODE`, a zero byte, the mode) and waits for OK / ERROR |
| Range | `meshcore_cli.py` 2583-2594 | `set path_hash_mode <n>`: refused for 3 and more; `4845`: "0 for 1, 1 for 2 and 2 for 3" bytes; `packets.py` 88: `SET_PATH_HASH_MODE = 61` |
| Wire meaning | `packet_format.md` 99-122 | path length byte: bits 0-5 hop count, bits 6-7 hash size minus 1; 3 = 4 bytes is reserved / invalid; 2 and 3 byte hashes "supported in current firmware"; line 61: "v1.12.0 firmware and older only handled legacy 1-byte path hashes" |
| Per contact | `reader.py` 108-124; `commands_contact.py` 112-175 | a contact's route carries its own hash mode in the top two bits of `out_path_len`; the app now shows it |

Real data: the DEVICE_INFO frame of the user's real board, kept as the unit-test fixture (`kRealDeviceInfo` in `test_core.cpp`, also in `tools/meshcore_sim.py`; Seeed XIAO nRF52840, v1.15.0), ends in `00 01`: **client repeat off, path hash mode 1 = 2-byte hashes**, firmware level 11, so the row
exists on this board. Implemented as a Settings > Radio row **Path hash size** with the arrow popup (1 byte / 2 bytes / 3 bytes, starts on the board's mode), one line of
explanation ("A larger hash means fewer collisions between repeaters, but leaves less room per message."), a second line per choice (2 and 3 bytes say "Firmware 1.12 or older: 1 byte only", from
`packet_format.md`); OK writes `3D 00 mode` and reads DEVICE_INFO back (the notice says what the board now reports). The board status shows "Path hash size 2 bytes", the contact details show the
hash size of a route. Below firmware level 10 the row is a gold notice "Firmware too old for this feature: Path hash size (needs firmware level 10, the board has N)". Nothing is guessed:
the command, the byte and the level all come from the references; **not tried on a board.** Setting it needs no confirmation box (the board keeps it; the previous value is one popup away).

### Two bugs found and fixed on the way (both existed in 0.1.2)

* **Notices could vanish at once.** `App::tick` computed `now - notice_ms_` with unsigned numbers; a notice set later in the same tick (the answer of the board was processed after `now` was read) gave a
  huge difference and was cleared immediately. Seen in the headless run ("Newbie added to the contacts" never showed). Fixed (`now > notice_ms_ &&`). Other notices may have been affected on the deck without anybody noticing.
* **Buttons drawn inside a list row swallowed the tap** meant for the row (they were clickable boxes without the row's handler). In the headless run a tap on the new "i" box did nothing until this was fixed. The same construction exists in the 0.1.2 Settings > Channels rows (Mute / Key / Remove), so a tap exactly on one of those boxes may have done nothing on the deck (not checked there). The boxes are not clickable any more; the x of the tap picks the button.

## 4. Protocol statements and how sure they are

V = read in the references, I = inferred or from memory, nothing here was seen on a board.

* V: STATS frames and their lengths; AUTOADD_CONFIG (config byte, max_hops from companion v1.14); ALLOWED_REPEAT_FREQ (pairs of u32, a zero ends the list); CONTROL_DATA push (SNR, RSSI, path length, payload) and the DISCOVER_RESP layout
  (`reader.py` 980-1025, `payloads.md` 259-283); REMOVE_CONTACT, ADD_UPDATE_CONTACT field order (`update_contact`), SET_OTHER_PARAMS both forms, SET_PATH_HASH_MODE, REBOOT text, SET_RADIO repeat byte; the advert packet layout (`payloads.md` 26-58, `packet_format.md`).
* **I - the discover request frame.** `send_node_discover_req` is not in the local copy of meshcore_py; the frame `37 | 0x80 | prefix_only | type_filter | tag(4 LE)` is from `payloads.md` (DISCOVER_REQ), `packets.py` (`SEND_CONTROL_DATA = 55`, `NODE_DISCOVER_REQ = 0x80`) and the way `meshcore_cli node_discover` builds the filter (one bit per node type: chat 2, repeater 4, room 8, sensor 16, all 0xFF) and
  matches the answers (tag as 4 little-endian bytes). The command's own answer is unknown (OK? MSG_SENT?): the app accepts any non-error answer and works from the CONTROL_DATA pushes. The flag byte is `0x80` (prefix_only cleared: full 32-byte keys, so a found node can be added; a firmware that sends 8-byte prefixes gives a row that cannot be added).
* **I - FACTORY_RESET carries the word "reset".** The reference client (`commands_device.confirm_factory_reset`) sends the command byte `0x33` alone, with a comment that "the firmware itself has no token verification". From memory of the firmware source the check is `cmd[0] == CMD_FACTORY_RESET && memcmp(&cmd[1], "reset", 5) == 0`,
  the twin of the "reboot" check that the reference does send. The app sends `33 72 65 73 65 74`. If the real firmware ignores trailing bytes this is harmless; if it needs the word, the reference form would have failed. One constant (`build_factory_reset`). **A board test decides.**
* **I - the unit of GET_ALLOWED_REPEAT_FREQ.** The references return raw integers. Taken as kHz (the unit of SET_RADIO); a pair below 10000 is read as MHz. The raw numbers are written to `mesh-hop.log` (`repeat: allowed frequency ranges as the board sent them`). If the firmware lists single frequencies (lo = hi) the user's 869.525 / 869.618 MHz will not be inside: the row then says why.
* I - the adverts in LOG_DATA reach the app on every board (the reference parses them; 0.1.x ignored the payload). If the board sends none, Nearby only shows the ADVERT / NEW_ADVERT pushes and the scan answers (no SNR for pushes).
* I - SET_AUTOADD_CONFIG sends only the flag byte (as `meshcore_py`); whether a firmware with the max_hops byte resets it to 0 is unknown (the app logs what it reads back).
* I - the 8 s scan window and the 5 s refresh of the statistics are my choices, not protocol facts.

## 6. Test protocol for the deck (the user tries; the Controller does the log steps)

Install `mesh-hop_0.2.0_arm64.deb` over 0.1.2 (the contacts, history, mute flags and retry settings of 0.1.2 are kept). `dpkg -s mesh-hop` must show `curl` in Depends. Use the real USB board (level 11). **Things that change the board or the mesh are marked (!): do them with the care written there.**

1. **Start and regression.** Start Mesh Hop; Chats left pane has the **Search messages** button; a direct chat has a **Details** button in its header; tabs, Esc (hint only), 3 s hold quits as before. *Controller:* `tail -n 40 ~/.local/share/mesh-hop/mesh-hop.log` and send me the lines `board: ...`, `autoadd: ...`, `repeat: allowed frequency ranges ...` (they say the level, path hash mode, repeat, manual add, what the board answered to GET_AUTOADD_CONFIG and the raw numbers of the repeat ranges).
2. **Board status.** Settings top: **Position** (your board's position, or "not set"; tap it: notice "Reading the position"), **Path hash size 2 bytes** (expected: the DEVICE_INFO frame of this board kept in the tests says mode 1), Board GPS row only if the board lists it, **Statistics** row.
3. **Statistics.** Open it: figures within about 2 s; Refresh; wait 10 s: "Updated" and the numbers move by themselves (Auto: 5 s); Auto switch off / on by touch; Esc closes it (not the app). If the notice "Firmware too old for this feature: Statistics" appears instead, say so (*Controller:* log `stats 0: error N`).
4. **Path hash size (!).** Settings > Radio > Path hash size: the popup shows "2 bytes", the arrows (touch and Left / Right), the line "A larger hash means fewer collisions ... less room per message". Choose 3 bytes, OK: notice "Path hash size set to 3 bytes", the board status line says 3 bytes. **Put it back to 2 bytes** (your original) before leaving, unless you want to keep a test value: repeaters on firmware 1.12 or older may not forward packets with longer hashes (packet_format.md), which can cut your reach. *Controller:* log `path hash mode 2: ok` (or `error N`) then `path hash mode 1: ok`. Optional: send a direct message to a far contact at 3 bytes and at 2 bytes and compare.
5. **Repeat (!).** The row tells what the board allows. If it says "Not allowed on this frequency (allowed: ...)", write the text down. If it is available, tap it, read the box, answer **No** (do not leave repeat on: the board would forward other people's packets). Only if you want to test the switch: Yes, then tap again at once to switch it off; the status says On / Off. *Controller:* the `repeat:` lines.
6. **Contact details.** Tap the **i** box at the right of a row (and press I on a selected row, and the Details button in a direct chat): name, type, groups, the two lines of the key, the route (for a repeater with a path: "N hops (2-byte hashes): ..."), last advert, heard here, position, distance. The buttons are easy to hit; Esc closes.
7. **Groups.** In the details press Groups > "+ New group with this contact...", type a name: it appears; tap another contact's Groups and tick it; Contacts > **Group: All** > the group: only its members; rename and delete from the same list. Quit and start the app: the groups are back. *Controller:* `cat ~/.local/share/mesh-hop/groups.jsonl; ls -l ~/.local/share/mesh-hop/groups.bak`.
8. **Bulk delete (!).** Choose contacts you do not need (for example **Select... > Never heard**, look at the count first, then unmark most of them: two or three are enough). The box must say "Delete 3 contacts?" with the names. Answer No (nothing happens), then Delete: the progress box counts "1 of 3 ...", the table loses exactly those rows, the notice says "Deleted 3 contacts". Tap Refresh: they are still gone (the board agrees; a node that adverts later comes back, that is normal). Try **Stop** if you delete 5 or more. *Controller:* log lines `contacts: bulk delete of N asked`, `bulk delete finished: Deleted N contacts` (and any `bulk delete: error ...`).
9. **Nearby and scan.** Contacts > Nearby: after a few minutes of listening the nodes heard appear with SNR and hops when the board sends its radio log (tell me if SNR is "no signal figure" everywhere: the board sends no LOG_DATA). Press **Scan**: for 8 s nodes in direct range answer ("direct", SNR). *Controller:* log `discover request: ok (code 0x..)` (or `error 1` = unsupported) and `discover: N nodes answered`; send me the code in parentheses.
10. **Add and Ignore (!).** Nearby only shows "waiting" nodes in manual mode: Settings > Contacts > **Add nodes by itself** (tap: it becomes "Off: new nodes wait in Nearby"; *Controller:* `manual add on (5 bytes): ok` or a retry `(4 bytes)`). Wait for a new node to advert (or use Scan), then in Nearby tap **Add** on one (notice "... added to the contacts", it becomes "contact") and **Ignore** on another (it disappears; the **Ignored** button brings it back, **Restore** puts it back). **Switch "Add nodes by itself" back to On** afterwards. *Controller:* `add contact xxxxxxxx (type N): ok`. A node found only by the scan has no name: its name is "Node abc123" until its next advert.
11. **Auto-add types (!).** Settings > Contacts > Still added by itself: a list with [x] marks (chat nodes, repeaters, room servers, sensors, replace the oldest); tap one: notice "Auto-add types saved on the board"; open the list again to see it; put it back. *Controller:* `autoadd set 0x..: ok`.
12. **Search.** Chats > Search messages (or Ctrl+F): type a word you know; touch the **Chat**, **dates** and **Show** buttons (or Ctrl+K / D / R); a typed range such as `2026-10-01 2026-10-08`; tap a result: its conversation opens with the message framed in gold. Close with the Close button or Esc.
13. **Scheduled advert.** Settings > Scheduled advert: Advert every > 1 h (arrow popup), Advert type > Zero-hop; the rows turn gold / show the choice; quit and start: kept. Leave the app open for 1 h: *Controller:* `grep -i "scheduled advert" ~/.local/share/mesh-hop/mesh-hop.log` shows one line per hour (`scheduled advert (zero-hop): ok`). Put it back to Off afterwards (the default).
14. **Reboot.** Settings > BOARD ACTIONS > Reboot the board: the box says nothing is erased; Yes; the footer shows the board gone ("Board disconnected") and it reconnects within about 20 s, contacts and settings intact. *Controller:* log `reboot requested` and the `link:` lines.
15. **Factory reset (!!, do NOT confirm on your real board).** Open it: first box (red Continue, "No" is the default), Continue: the second box has a grey **"Yes, erase (3)"** that counts down and does nothing when tapped or answered with Y before 3 s. Answer **"No, keep it"**. A real reset only on a spare USB board (it erases the board's key = its identity, contacts, channels): the log says `factory reset: the board answered OK` or `factory reset refused: error N` (error 1 would mean the firmware wants the other frame, see section 4).
16. **Preset retry.** With the deck online but the download failing at start (for example start the app a few seconds before Wi-Fi has its route, or block `api.meshcore.nz`): *Controller:* the log shows `refresh failed (...); one more try in 60 s`, then a minute later `online, downloading ... (second try)`; with Wi-Fi up it ends with `fetched N entries` and no popup or notice appears.
17. **Escape and size.** Esc closes one layer at a time (box, editor, search, statistics, details, Nearby, select mode) and on a top-level screen only shows "Hold Esc 3 s to exit"; a 3 s hold quits. Say if any new button, check box, Add / Ignore box or the **i** box is hard to hit with a finger.

In particular unknown until a board answers: the reply to the discover request, whether LOG_DATA carries adverts on this firmware, the unit of the repeat ranges, the factory reset word, SET_AUTOADD_CONFIG and max_hops, GET_STATS support on v1.15.0 (the references show the frames, the user's firmware is level 11).
* Touch on the real panel: the **i** column (x >= 584 of a 44 px row), the Add / Ignore boxes, the check boxes; a finger on the Nearby rows while they are rebuilt (they are not rebuilt under a finger, as in the other lists). The 3 s waiting Yes with a real finger.
* The look on the real panel of the new gold lines and of the list box; memory and speed on the Pi (the Nearby list is bounded to 150 rows, the search to 300, both virtual lists; selecting rebuilds the row specs of the table, 161 rows, a few milliseconds on the PC).
* BLE: only designed (section 9).

## 8. Risks

* **Bulk delete is destructive and one by one on a slow link**: 161 deletes take minutes on a busy board; Stop ends after the one in flight; a link loss ends the job with a notice. The box always names the count and "cannot be undone".
* **Factory reset** erases the board identity; two boxes, the second delayed, and the app clears its cache of the board's contacts and channels. If the firmware refuses the frame nothing is erased and a notice says so. The history, groups and settings of the deck stay.
* **Path hash size** at 2 or 3 bytes may not be forwarded by repeaters on firmware 1.12 or older (`packet_format.md`); the popup says it on the 2 and 3 byte choices. The user's board already runs mode 1.
* **Repeat** turns the companion into a forwarder: the Yes box says it; the row only offers it where the board lists the frequency.
* **Manual add mode left on** means no new node is added until the user adds it: the row says "Off: new nodes wait in Nearby" in gold. Pending nodes are lost at restart (the board never held them).
* Nearby names and positions come from unsigned adverts (the app has no Ed25519): anybody on the air can forge a name; Add sends the key to the board like any other client.
* The scheduled advert needs the app to run and the board to be connected; a flood advert every hour is a lot of airtime for a big mesh (the box says "Flood ... use it rarely").
* The contact cache is rewritten on every contact change as before (once per batch for a bulk delete); `groups.jsonl` is rewritten on every group change (tiny).
* The two bugs of section 3 changed behaviour of 0.1.2 screens (notices stay 4 s now; taps on Settings channel buttons are decided by the x of the tap only).

## 10. BLE: design note and a one-day spike (not implemented, as asked)

**Facts from this repo and the build sysroot** (no deck access, so these are the libraries of the image the SDK was built from, `SDK/github_source/static_lib_v0.0.7`, Debian 13 aarch64): libdbus 1.16.2 (`libdbus-1.so.3.38.3`, headers in `usr/include/dbus-1.0`), libsystemd 257 (`libsystemd.so.0.40.0`, `systemd/sd-bus.h`), glib / gio 2.84.4, libbluetooth 3.19.15, even `sdbus-c++` headers. The launcher already talks to BlueZ in two ways: `ext_components/bluectl` (pure C over libdbus-1, no glib; adapter, device, pairing agent, **no GATT**) and `cp0_bluez_dbus_client.cpp` (GDBus over `gio/gio.h`, with a pairing agent). The Bluetooth keyboard is already a BlueZ LE device, and Settings > Bluetooth of the launcher (`settings_bluetooth_page.cpp`) already handles `RequestPinCode` / `RequestPasskey` with typing on the keyboard. So no new package is needed on the deck, whatever the choice.

**1. Interface changes in `core/transport.hpp` (and `client.cpp`).**
* Framing: the companion doc says BLE sends one protocol frame per characteristic write or notification, **without** the serial wrapper (`0x3C` / `0x3E` + 2-byte length). Today `Client` owns a `FrameParser` and calls `encode_frame` (serial). Add `virtual bool message_oriented() const { return false; }` to `ITransport`; when true `Client` skips the parser (each `read()` returns exactly one frame, framed by a 2-byte length prefix chosen by the transport, or better: a new `long read_frame(Bytes &)`) and writes the bare payload. Smallest change: the BLE transport re-creates the serial framing around notifications and strips it from writes, so `Client` stays untouched; use that for the spike, switch to `message_oriented()` for the product (about 15 lines in `Client::pump_queue` / `poll`, plus a fake in the tests).
* `OpenStatus` gets `Pending` (a BLE open is several steps: connect, services resolved, characteristics, notify acquired: `open()` stays non-blocking and returns `Pending` until ready; the Client already retries `try_open()` on a timer), `NotPaired`, `BluetoothOff`.
* Target selection: a `TransportConfig` saved next to the `port` file (`transport` = `usb` or `ble:AA:BB:CC:DD:EE:FF`) and a factory in `App` that builds a `SerialTransport` or a `BleTransport`; `LinkInfo` gets `address`, `name`, `rssi`, `bonded`; `kind()` returns "Bluetooth LE" (already foreseen in its comment). Settings > BOARD gets a "Connection" row (USB / Bluetooth: a list of bonded devices that expose the Nordic UART service).
* `write()` returns true when queued (BLE writes are asynchronous); `read()` returns -1 when `Device1.Connected` turns false. Everything else (command queue, timeouts, handshake DEVICE_QUERY then APP_START) is transport independent. A BLE board answers no data until bonded: `NotCompanion` handling must not fire while pairing is pending.

**2. BlueZ D-Bus GATT client on the deck.** Library choice for the transport (`ble_transport.cpp`, one worker thread or a poll from the UI tick; no GLib main loop in the app):
* **sd-bus** (`libsystemd0`, always present, public API, `sd_bus_call_method_async`, `sd_bus_match_signal`, `sd_bus_get_fd` + `sd_bus_process` fit the 20 ms poll): least code, no new `Depends` line beyond what systemd gives. Recommended for the spike.
* libdbus-1 (proven on this deck by `bluectl`, whose helpers can be copied; more verbose for variants and dictionaries) is the fallback; GDBus would drag glib / gobject / gio (3 libraries) into an app that links 2 today.
Calls: `Adapter1.SetDiscoveryFilter({UUIDs:[NUS], Transport:"le"})` + `StartDiscovery` only on user request for 8 s; for a known address skip scanning and use `Device1.Connect()` on the object path `/org/bluez/hci0/dev_XX_XX_XX_XX_XX_XX` (async with a 20 s timeout); wait for `ServicesResolved == true` (PropertiesChanged); `GetManagedObjects` to find the characteristics by UUID; **`GattCharacteristic1.AcquireNotify`** (returns a file descriptor and the MTU: each `read()` is one notification, non-blocking, ideal for `ITransport::read`) and **`AcquireWrite`** or `WriteValue({type:"request"})` for commands (the doc recommends write with response). MTU: BlueZ exchanges it as GATT client; frames up to 172 bytes need it (DEVICE_INFO is 82 bytes, a contact 148); the spike prints the value.
Permissions: the launcher user already drives `org.bluez` over the system bus, so `osrde` (group `bluetooth`) is enough, nothing in D-Bus policy or services changes (an approval gate item if it ever did).

**3. Nordic UART service and framing differences from the companion doc.** Service `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`; RX characteristic (app -> firmware, write) `6E400002-...`; TX characteristic (firmware -> app, notify) `6E400003-...`. Differences to the USB path: no `<` / `>` length wrapper; one frame per write / notification; the first command after connecting is the same (`APP_START`, `DEVICE_QUERY`, `SET_DEVICE_TIME`, `GET_CONTACTS`, `GET_CHANNEL` x N, `SYNC_NEXT`); notifications must be enabled first; one command at a time with a 5 s timeout (the Client already does it); the board "may disconnect after periods of inactivity" (reconnect with exponential back-off). Everything above the transport (`protocol.cpp`, `client.cpp`, `model.cpp`) is unchanged; the BLE firmware and the USB firmware are different builds (the user's BLE board has no USB companion serial).

**4. Pairing and PIN without an on-screen keyboard.** MeshCore BLE boards ask for a passkey (DEVICE_INFO carries `ble_pin`; a fixed default is common; a board with a screen may show a random one). With BlueZ this is the agent method `RequestPasskey`. Best path: **pair once in the launcher's Settings > Bluetooth**, which already collects the passkey by typing on the Bluetooth keyboard and bonds the board (`Paired`, `Trusted`); Mesh Hop then only connects to a bonded device and never sees the PIN. If the launcher page does not list or pair a "MeshCore-..." LE device that is not an input device, the fallback is an agent in the app (`AgentManager1.RegisterAgent` with capability `KeyboardOnly`, the PIN typed in the app's own editor); but a second default agent competes with the launcher's: only do it if the first path fails (spike question). The app never stores the PIN.

**5. Reconnection.** The transport keeps the address; on `Connected == false` it reports -1 (the Client then shows "Board disconnected" and retries `open()` every 2-4 s with back-off up to 30 s); `Device1.Connect()` on a board that is not advertising blocks until it times out, so it is always asynchronous; `Trusted=true` lets BlueZ reconnect by itself when the board comes back, which the transport also notices through `PropertiesChanged`. On exit `Device1.Disconnect()` (the bond stays). The phase 1 rule "nothing may depend on the keyboard being present" extends: nothing may block on the board either.

**6. Coexistence with the Bluetooth keyboard and Wi-Fi.** The keyboard is an LE HID-over-GATT device on the same controller (CYW43438 class chip of the Pi Zero 2 W: Bluetooth 4.2, shares the 2.4 GHz radio with Wi-Fi). The decision of 2026-10-08 says "can hold several LE connections: to prove". Risks to measure: key latency while the board streams (GET_CONTACTS of 161 contacts is about 25 KB), while Wi-Fi is busy, and while the adapter is scanning (never scan continuously; scan only on request for 8 s, with a UUID filter and no duplicates); connection interval negotiation (BlueZ default, 30-50 ms) and supervision timeouts when both devices are active; whether the keyboard reconnects after sleeping while the board link is up.

**7. A one-day spike the Controller can run on the deck with the user's BLE board** (all read-only on the system, no boot, service or udev change; the board must run the BLE companion firmware and be near the deck; the user keeps the board's PIN at hand):
1. (30 min) Inventory over ssh: `dpkg -l | grep -E 'bluez|libdbus|libsystemd|libglib|sdbus'`, `bluetoothctl --version`, `systemctl status bluetooth`, `btmgmt info` (supported settings, LE on), `ls /usr/lib/aarch64-linux-gnu | grep -E 'libsystemd|libdbus'`. Expect BlueZ 5.8x, libdbus 1.16, libsystemd 257.
2. (1 h) `bluetoothctl`: `scan on`, find the board (name starts with the MeshCore prefix, advertises 6E400001...), pair with the passkey (also try the same through the launcher's Settings > Bluetooth, the cleaner path), `connect`, `menu gatt`, `list-attributes`, `select-attribute` the TX characteristic, `notify on`, then `write` the APP_START frame (`01 03 20 20 20 20 20 20 6d 63 63 6c 69`) to the RX characteristic: a `0x05` SELF_INFO notification must come back. Record the MTU (`bluetoothctl` shows it on `acquire-notify`) and the connect time.
3. (2 h) A 150-line C program (sd-bus, scratch folder outside the repo, not committed) that connects to the bonded address, waits for `ServicesResolved`, finds the characteristics, `AcquireNotify` + `AcquireWrite`, sends DEVICE_QUERY / APP_START / GET_CONTACTS, prints the frames as hex with timestamps; run it against the real board for 30 minutes with a message sent from another node. Measure: first frame latency, GET_CONTACTS time, frame sizes vs MTU.
4. (1 h) Reconnect: power-cycle the board, walk out of range and back, `rfkill`-less `bluetoothctl disconnect`; time to reconnect with `Trusted=true` and with an app-side `Connect()` loop.
5. (2 h) Coexistence: with the Bluetooth keyboard connected, type for 5 minutes while the spike streams (a GET_CONTACTS every 20 s) and Wi-Fi runs a download; compare key latency (`evtest` timestamps) against the same minutes without the BLE link; repeat with a 8 s discovery running.
6. (1 h) Write the go / no-go note: numbers, the pairing path that worked, the library (sd-bus or libdbus-1), the size of `BleTransport`, and the exact `transport.hpp` diff. Then phase 3 implements it (about 600 lines plus tests: a fake GATT peer for the unit tests, the simulator gets a `--ble` pty bridge that wraps / unwraps frames).
Success criteria: SELF_INFO received over BLE; the same session works for 30 min; reconnect under 15 s after a power cycle; no visible key lag. If pairing needs an app-side agent, add half a day.
